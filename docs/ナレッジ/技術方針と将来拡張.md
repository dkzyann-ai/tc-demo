# 技術方針と将来拡張

最終更新：2026-08-01

## 1. 前提

設計資料（要件定義書 v0.1）には、使用言語・フレームワークの指定はない。一方で、本番ではPCブラウザ利用、学校・塾単位での共有、認証・権限、問題・テストの保存、画像添付、2D関数グラフ、印刷またはPDF出力を想定している。

このため、DEMOのWindows単体配布と将来のWebサービス化の両方に対応できる構成を採用する。

## 2. 技術選定

主言語はTypeScriptとする。

| 領域 | DEMO | 本番 |
| --- | --- | --- |
| 画面 | React + TypeScript | React + TypeScript |
| 実行形態 | Windows向けデスクトップアプリ | PCブラウザ向けWebアプリ |
| バックエンド | アプリ内のローカル保存を利用し、独立サーバーは設けない | Node.js + TypeScriptによるAPI（NestJSを第一候補） |
| データ | ローカル永続化 | PostgreSQL |
| DBアクセス | 実装時に決定 | Prismaを第一候補 |
| 印刷 | HTML/CSSのA4プレビューとOS印刷 | HTML/CSS印刷を基本とし、必要に応じてPDF生成 |

DEMOのReact画面・ドメインモデル・印刷レイアウトは、本番Web版で再利用する。本番化では画面を作り直すのではなく、ローカル保存層をAPI呼出しへ置き換え、認証・共有機能を追加する。

## 3. セキュリティ設計の原則

ブラウザやデスクトップアプリの画面側は、利用者が内容を確認・改変できる前提で扱う。画面に見えない変数であっても、秘密情報を置いてはならない。

- パスワード、APIキー、DB接続情報を画面側に置かない。
- 本番の認証、組織所属の確認、閲覧・編集・削除の権限判定は、すべてバックエンドAPIで実施する。
- 画面でボタンを非表示にするだけで権限を制御しない。APIごとに権限を再検証する。
- 組織IDはリクエストで任意指定させず、ログイン済みユーザーの所属情報を基にサーバー側で確定する。
- 認証情報は、可能な限り`HttpOnly`かつ`Secure`なCookieで扱い、画面側のJavaScript変数に保存しない。

DEMOは単一利用者・ローカル保存であり、本番用の認証や共有は実装しない。ただし、問題・テスト・ユーザー（将来）・組織（将来）の責務を分離し、本番移行でデータ構造を作り直さない。

## 4. データ量・性能への対応

現時点の要件（教員1名あたり問題数百件、2D関数グラフ、テスト作成・印刷）では、TypeScript + Node.jsで十分対応できる。性能は言語だけで決まらないため、次を優先する。

- PostgreSQLのテーブル設計と検索用インデックス
- 一覧・検索のページ分割
- PDF一括生成・集計等の重い処理を非同期ジョブとして分離
- キャッシュ、監視、バックアップ
- API・データアクセス層の責務分離

## 5. Javaを採用・併用する判断基準

Javaは、次の条件が明確になった場合に、重い処理を担うバックエンドサービスとして採用を検討する。

- 多数の学校・教員が高い同時接続数で利用する。
- 大量の帳票やPDFを継続的に一括生成する。
- AI採点、統計分析、推薦問題生成など、重いバックグラウンド計算を常時実行する。
- 長期保守・厳格な運用基準があり、Javaに習熟した開発・運用体制がある。

これらの条件がないうちは、複数言語化による開発・保守の複雑さを避け、TypeScriptを中心に開発する。将来Javaを追加する場合も、計算・帳票・分析などを独立APIとして分離し、通常の画面・認証・問題管理はTypeScriptのAPIで維持する。

## 6. 今後の正式決定事項

- 本番の認証方式（SSO、会員登録、教員コード等）
- 組織内共有の範囲と権限
- インフラ、ホスティング、DB運用方針
- PDF生成の要否と品質要件
- Javaサービスを追加する性能・運用上の判断基準
